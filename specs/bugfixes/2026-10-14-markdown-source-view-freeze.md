# Markdown 源码视图无响应

状态：客户端源码修复、本地测试、隔离浏览器预览与独立 macOS 测试包完成；当前运行的旧安装包未替换，新包尚未启动做原生交互验收，跨系统验收待完成。

## 问题与范围

用户在已打开的 Markdown 文件预览中点击“源码”，界面没有切换；截图与运行中客户端的辅助功能树仍显示菜单及实时预览。该客户端渲染进程在观察时持续占用约 65% CPU。仓库当前实现会把 `contentVersion` 和 `sourceView` 放入整个预览错误边界的 React key；每次切换模式或更新内容都会卸载可编辑 Markdown。卸载回调又在保存状态下无条件派发一个新的 `contentVersion`，形成可反复触发重建的链路。

仅修正星途客户端的 Markdown 文件预览身份和关闭同步。可编辑 Markdown 对同一文件切换源码/预览、收到内容版本更新时保持编辑器实例；关闭后仅在磁盘已保存内容与 artifact 内容不同时同步。其他文件类型仍按现有版本与模式重置。维持 CodeMirror 文档、选区、撤销、草稿、冲突处理和 IPC 保存协议。gateway、OpenClaw、对话输入输出及插件执行不在范围。

## 验收与验证

- 同一可编辑 Markdown 文件反复切换源码/预览后，能看到原始 Markdown 与实时预览，菜单更新，编辑器实例、选区和撤销历史保留。
- 内容同步不会因相同内容的卸载再次派发新版本；真正保存后的内容仍可同步到 artifact。
- 使用隔离样例验证切换与无持续渲染循环；运行改动文件 ESLint、相关 Vitest、类型检查和隔离构建。活动客户端不重启，不使用真实文档做编辑试验；真实安装包和跨系统验收单独记录。

## 结果

- `ArtifactRenderer` 为可编辑、文件型 Markdown 使用由 artifact ID 与文件路径组成的稳定边界 key。源码/预览切换及 `contentVersion` 更新现在只让同一 CodeMirror 实例重新配置显示；其他文件类型仍按内容版本和显示模式重置。`PreviewErrorBoundary` 同时接收独立的重试标识：健康编辑器不重建，失败界面仍可随视图或版本变化恢复。
- `EditableMarkdownFile` 卸载后等待保存结束，仅在最终已保存内容与当前 artifact 内容不同时派发同步，避免相同内容带新时间戳反复触发预览重建。文件编辑、保存、冲突和草稿协议未改变。
- Node 24.21.0、macOS：边界恢复、身份与 Markdown 预览/编辑定向测试共 5 文件、27 项通过；改动 TS/TSX 严格 ESLint、`npx tsc --noEmit`、`git diff --check` 与隔离目录 `.work/markdown-source-fix/build` 中的 `npm run build` 通过。最终构建日志为 `.work/markdown-source-fix/build-final.log`。
- 隔离浏览器预览挂载实际 `ArtifactRenderer`、Redux 与 CodeMirror，使用虚构 Markdown 文件和模拟文件 IPC。首次读取旧 artifact 后只同步 1 次；5 轮源码/预览往返后仍为同一编辑器、仅 1 次 artifact 更新，源码显示原始 Markdown。模拟编辑自动保存使更新数到 2，切换后撤销恢复原文并再次保存，更新数到 3。补加失败边界恢复后，又复核了一轮源码/预览往返，编辑器仍保持且更新数为 1。截图为 `.work/markdown-source-fix/source-view.png`；预览服务已停止。
- 活动旧包的菜单在观察时对点击和 Escape 都无响应，渲染进程采样时约 65%–105% CPU；这些现象与上述重建循环一致，但原生进程样本没有可符号化的 JavaScript 栈，故不把采样单独当成根因证明。未重启或改写活动客户端，也未对用户文档输入或保存；新包、真实文件、Windows/Linux 和 GitHub CI 未在本轮验证。gateway 保持只读，没有提交或推送。
- 用户随后提供活动监视器截图：旧包渲染进程 PID 40013 占用约 5.49 GB，另有 `node` PID 92053 约 3.73 GB。只读复核时，旧包渲染进程 RSS 约 5.0–5.2 GiB、CPU 一次达 485.8%，而该 `node` PID 已退出；因此确认旧包仍异常运行，但无法从截图确定 `node` 的历史命令或把全部内存增长归因于同一代码链路。源码修复不会热更新到旧包，释放现有占用与原生验证需要退出旧进程并启动隔离打包的修复版；尚未对活动客户端执行该切换。
- 后续截图显示同一 PID 40013 在活动监视器中升至 9.26 GB；只读 `ps` 随后测得其 RSS 约 5.16 GiB、CPU 514.5%，再过数秒该进程消失，主进程 39999 仍在并创建新的渲染进程 PID 94691（约 217 MiB、空闲）。最近 30 分钟的诊断报告目录未见匹配的新报告，不能确定旧进程是被系统终止、应用重建还是用户手动结束。新进程仍加载相同旧包，旧缺陷有再次触发风险。
- 为准备原生验证，独立复制活动包到 `.work/markdown-source-fix/native-preview/NovaPath.app`，仅在副本中解出 app 目录并替换为隔离构建产物 `dist`/`dist-electron`；没有修改活动包、其运行目录、用户配置或文档。副本重新做本机临时签名，`codesign --verify --deep --strict` 通过，构建产物与副本入口文件逐字节一致。该测试包不是正式发布包，未公证，也尚未启动或执行真实文件交互；活动旧包仍在运行。
- 后续 UI 位置微调的隔离构建首次发现 `PreviewErrorBoundary` 先前只更新了调用和测试，组件本身尚未实现 `resetKey`；现已补齐组件接口及失败状态恢复。随后相关 2 文件 5 项测试、改动 TSX 严格 ESLint、隔离 `npm run build` 与 `git diff --check` 通过。独立测试包已同步最新构建并重新做本机临时签名，严格签名校验再次通过；仍未启动做原生交互验收。
