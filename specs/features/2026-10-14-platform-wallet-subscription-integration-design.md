# 星途平台钱包、积分展示与套餐对接方案

状态：方案草案已按订阅机制审核更新，套餐研究与产品定档先行；客户端对接开发待成本和运营规则确认。本文件不代表购买或支付已经开通。核对日期：2026-10-14。

## 目标和边界

让星途客户端以公司平台为账户、额度和套餐的唯一事实来源，形成“看余额与订阅 → 理解扣费顺序 → 查看实际消耗 → 前往购买 → 返回后核验”的闭环。星途只做客户端适配；兄弟项目 `maas-token`、其克隆、分支、worktree、部署与数据库始终只读。

- 钱包与订阅是**两套额度池**。两者使用平台 quota 基础单位，但不能相加成一个“剩余积分”。
- “积分”是展示单位，不是客户端新造的账户或账本。只在平台 `/api/status` 返回 `CUSTOM` 且符号为“积分”时显示积分；`CNY` 显示人民币，`USD` 显示美元，`TOKENS` 显示原始额度。套餐价格另用计划自身的币种，不用 quota 汇率推算售价。
- 星途登录会话与模型 API Key 独立。未核实密钥所属账户前，不宣称一次模型请求必然扣当前登录账户的钱包或订阅。
- 不恢复旧上游账户的积分领取、优惠券、试用或品牌购买流程；不修改回答渲染、输入输出、插件/技能/MCP 执行。
- 不在真实平台创建订单、发起支付、充值、改扣费偏好或测试扣款。购买功能发布前要有明确的产品和支付验收。

2026-10-14 读取线上公开 `/api/status` 的结果为 `quota_display_type=CNY`、`quota_per_unit=500000`、`usd_exchange_rate=7`。客户端必须动态读取，不能把当前配置写死为积分。真实账户的套餐列表在本次客户端窗口中为空；仅凭空列表不能判断是未配置计划，还是平台支付合规开关未启用。

## 现有事实来源

| 信息或动作 | 平台现有接口 | 客户端现状 | 设计处理 |
| --- | --- | --- | --- |
| 展示单位、汇率 | `GET /api/status` | `maas:billing` 已读取 | 只用于 quota 展示换算，配置非法时显示不可用与原始额度，不猜汇率 |
| 钱包余额、累计用量、请求数 | `GET /api/user/self` | 已通过主进程同步到账户卡 | 按账户 ID 和平台 Origin 隔离，显示同步时间与过期状态 |
| 套餐目录 | `GET /api/subscription/plans` | 已只读接入 | 只展示平台启用的计划；空态需结合 `/api/user/topup/info` 的合规状态说明 |
| 我的订阅、扣费偏好 | `GET /api/subscription/self` | 已只读接入；当前仅展示状态与有效期，额度字段已解析但未展示 | 每份订阅独立展示；精确剩余额度待结算超额和重置边界验证后再开启 |
| 支付开关与方法 | `GET /api/user/topup/info` | 未接入 | 决定是否展示购买入口；只投影必要的公开能力字段 |
| 我的充值记录 | `GET /api/user/topup/self` | 未接入 | 第二阶段只读历史，按服务端分页，不与订阅订单混同 |
| 请求消耗与来源 | `GET /api/log/self`、`GET /api/log/self/stat` | 未接入星途账单页 | 分页显示模型、时间、quota 和日志 `other.billing_source`；没有来源时写“未提供” |
| 修改扣费顺序 | `PUT /api/subscription/self/preference` | 未接入 | 由用户显式选择，服务端确认后重新读取，不做静默更改 |
| 钱包余额购买套餐 | `POST /api/subscription/balance/pay` | 未接入 | 属于立即扣款；必须明确价格与钱包扣额、二次确认、单次提交和服务端核验 |
| 第三方支付 | `/api/subscription/{epay,stripe,creem,waffo-pancake}/pay` | 未接入 | 客户端不采集卡号；优先跳平台 `/wallet` 完成支付，回到星途后重新同步 |

平台 `subscription_first`、`wallet_first`、`subscription_only`、`wallet_only` 四种偏好由服务端执行。`wallet_first` 余额不足时可尝试订阅；`subscription_first` 在订阅额度不足时，任一有效订阅设置 `allow_wallet_overflow=false` 就会阻止整体回退钱包。多份订阅按先到期顺序尝试，一次请求只从一份扣，单份不足时尝试下一份，不拆分扣额。客户端只解释当前偏好与这些已核实规则，不自行模拟每次请求的最终扣费决策。

## 客户端信息架构

1. **账户概览**：显示当前账户、钱包余额、累计使用、请求数与最近同步状态。余额卡使用平台展示单位，不写成固定“积分余额”。
2. **我的订阅**：首批维持现有名称、状态与有效期展示。待平台结算超额与重置边界验收后，再为每份订阅单独展示服务端返回的已扣/总额度、下次重置及同步时间；`amount_total=0` 按平台语义显示“不限额度”。过期、取消与活跃记录分组；计划已下架时保留订阅 ID 和可用字段，不伪造计划名。百分比或区间仍基于同一份服务端数据，既不能用来掩盖数据过期，也不能作为规避精确值风险的替代展示：在结算超额与重置边界验收前，订阅额度的精确值、百分比和区间一律不展示。
3. **扣费顺序**：用四个可理解的选项解释钱包和订阅先后及“仅使用”语义；切换前明确可能导致请求因某一池不足而失败。仅显示服务端已保存的值。
4. **可用套餐**：卡片显示平台提供的标题、副标题、价格/币种和有效期；周期额度及重置方式待产品配置和结算边界验收后展示。推荐标签与卖点只有平台计划 ID 和公司文案正式确认后才启用，默认空。
5. **使用与购买**：请求明细给出实际扣费来源；“管理钱包/购买套餐”在第一阶段打开平台 `/wallet`，支付由平台页面完成。客户端仅在后续同步确认后显示新余额或新订阅。

页面不显示钱包与订阅的合计数字，也不把 `price_amount` 按 quota 展示汇率再算一遍。模型密钥属于哪个账户未能验证时，在额度旁保留“模型扣费取决于密钥所属账户”的提示；同一会话里不把登录账户余额当作该密钥的可用余额。

## 数据和 IPC 设计

- 继续由主进程持有 JWT、SID、HttpOnly Refresh Cookie 和加密存储；renderer 只收到白名单字段。所有新增 IPC 维持现有 `event.sender` 来源校验、固定平台 Origin、请求超时、响应大小限制和严格 DTO 解析。
- 为每份快照保留 `origin + accountId + syncedAt`；退出、换账号或刷新确认失效时清空。网络故障保留上次成功结果并标记“上次同步”；迟到响应不能覆盖新账户。
- 账户概览的 `WalletSnapshot` 沿用现有 `MaasBillingSnapshot`；订阅 DTO 继续保留每条记录，不将周期额度并入钱包。需要解释回退规则时，白名单投影订阅实例上的 `allow_wallet_overflow`，不能只取当前套餐字段：已售实例有独立快照。扩展计划字段时只加入显示/购买必需项，如 `allow_balance_pay`、购买次数限制和服务端允许的支付方式；不把 Stripe/Creem 产品 ID 当作客户端订单凭据。
- 新增只读 `paymentCapabilities`、`usageHistory`、`topUpHistory` 时分别建契约和分页游标；金额、quota、时间戳和状态严格校验。金额显示与 quota 换算使用各自字段。
- 刷新触发：登录恢复、打开相关页、窗口重新聚焦、网络恢复、模型请求完成/失败、购买页返回和手动刷新。请求合并、节流；失败不能将已有余额错误归零。
- 若模型 API Key 归属无法从现有接口可信验证，只展示账户级快照。不要通过字符串比较密钥、读取管理 PAT 或把登录 JWT 当模型 Key 来“关联账户”。

## 购买与支付分阶段设计

### 阶段 A：安全可发布的查询和平台入口

完成钱包/订阅/扣费顺序的分开展示、使用来源只读明细、合规与套餐空态；订阅精确剩余继续隐藏，直到平台方完成结算与重置边界验收。购买入口只打开固定平台 Origin 的 `/wallet`。系统浏览器可能要求重新登录，客户端不传 JWT、Cookie、密码或支付信息。窗口回焦后刷新钱包与订阅；跳转返回不等于支付成功。

### 阶段 B：扣费偏好

新增 `maas:billingPreference` IPC 对 `PUT /api/subscription/self/preference`。客户端仅允许四个枚举值，显示当前服务端值；用户点击保存后等待成功响应，再 GET `/api/subscription/self` 确认。失败则保持旧值与错误提示。测试账户切换、并发点击、401、网络中断与服务端规范化返回。

### 阶段 C：原生购买（上线门槛较高）

只有平台计划、支付合规、支付方式、条款和退款说明准备完毕后才启用。选择计划后重新拉取最新计划与账户余额，确认弹窗列出计划 ID、名称、实际价格币种、有效期、额度和可能扣除的钱包 quota。余额支付会立即扣款并创建订阅，客户端必须禁止重复点击、超时自动重试和后台静默提交。第三方支付仅接收并验证 HTTPS 结账链接，交给平台/可信支付页面，不在星途采集银行卡数据。支付完成依赖服务端订阅/钱包/订单状态再查询，不依据浏览器返回 URL 宣称成功。

当前 `balance/pay` 请求只有 `plan_id`，未提供客户端幂等键；超时后客户端无法安全判断是否已经扣款。**在服务端提供可查询订单号或幂等能力之前，原生余额购买只保留设计，不开启用户入口**。这不是要求本轮修改 gateway，属于平台接口缺口。客户端仍可使用阶段 A 的平台钱包页完成购买。

## 异常与验收规则

- 钱包为 0、订阅仍有额度：分别显示，不提示“积分用尽”。订阅为 0、钱包仍有额度：`subscription_first` 下任一有效订阅禁止兜底就不能回退；仍以服务端实际扣费结果为准。
- 无套餐：若 `/api/user/topup/info` 显示支付合规未启用，说明平台暂未开放；合规已启用但列表空，说明当前无可用计划。失败与真正空列表要区分。
- 订阅重置、到期、取消、无限额度、多份活跃订阅、计划下架、请求退款、日志缺少 `billing_source` 都有明确展示，不合并或猜测。`/api/subscription/self` 读取时不会主动重置；主节点定时任务约每分钟扫描一次，重置边界短时旧值应标记数据同步时间并在刷新后重新读取，不能由客户端推算新余额。
- 登录过期与网络故障区别处理；真实窗口曾在打开账户页时返回登录页，需通过隔离契约服务和真实账户复现并查明原因后，才能认定为客户端缺陷。
- 单位测试：CNY/USD/CUSTOM/TOKENS、非法汇率、钱包/订阅分离、余额不足与偏好四态、DTO 跨账户、旧响应竞态。
- 集成测试：主进程 IPC 凭据边界、刷新与 401、套餐与支付能力、日志分页、购买结果回读；支付只使用本地虚构平台，不产生真实订单。
- 原生验收：浅深色、中文英文、360/800/1200px、键盘与焦点、断网恢复、无套餐、有套餐及多订阅；Windows/Linux 单列。发布前用真人账户只读核对钱包、订阅和实际扣费来源，真实支付另行按公司流程验收。

## 平台接口缺口与依赖

1. **原生余额支付幂等/订单查询**：现有 `balance/pay` 仅收 `plan_id`；超时安全重试需要服务端幂等键或可按客户端请求号查询的订单。客户端不能自行补 gateway。
2. **模型密钥归属证明**：登录账户与手填 API Key 独立，现有客户端没有可信的同账户断言。没有证明前只能展示账户级额度，不能预测这次模型调用扣哪个账户。
3. **历史计划快照**：`/api/subscription/self` 的订阅实例只给 `plan_id` 等字段；计划下架后名称/原价可能无法从可用目录恢复。客户端显示可用字段并标记计划信息不可用。
4. **支付后订单状态**：第三方支付回跳不构成成功证据；现有客户端尚无订阅订单只读接口契约。第一阶段以订阅和钱包重新同步作最终用户反馈，未到账时展示“等待平台确认”。
5. **平台运营配置**：线上公开状态当前为 CNY，当前账户看到可用套餐为空。要展示“积分”及出售套餐，需要平台运营方通过现有后台配置展示单位、计划、价格与支付合规；本项目不修改该后台或数据。
6. **已售套餐的重置规则**：订阅实例快照了额度、分组与钱包兜底等字段，但重置仍读取当前计划。平台运营方应保留已售计划记录，不物理删除、不直接改重置周期；修改权益时建立新计划并下架旧计划。`duration_unit=month` 搭配 `quota_reset_period=monthly` 会在订阅有效期内再次刷新，月末日期规范化时还可能跨两次月初；首批每次购买一份额度的月包建议 `quota_reset_period=never`。星途仅能如实显示服务端返回的结束与下次重置时间，不承诺固定 30 天。
7. **结算超额与对账**：实际用量超过预扣且超出订阅上限时，平台补扣可能失败，而常规文本路径仍记录用量并继续处理成功响应。这是 Gateway 计费边界，需平台方在隔离环境验证并给出处置办法；客户端不能补扣、推算“正确”余额或宣称精确用量等于已扣额度。

## 实施顺序与责任

1. **客户端**：补只读支付能力、使用来源和充值历史，整理钱包/订阅页面；保留现有已验证的登录、账单和套餐只读链路。
2. **客户端**：接扣费偏好，增加真实账户只读验收和跨账户保护。
3. **平台运营方**：确认展示单位、计划、价格、支付方式、合规/退款文案、测试账号及可重复验收环境；锁定已售计划的重置规则并保留计划记录。
4. **平台计费负责人**：在隔离环境验证结算超额、重置边界和订阅扣额与用量日志对账，明确异常处置；该结果是开放精确订阅剩余展示的前提。
5. **共同验收**：先完成平台网页购买闭环；只有幂等与订单查询能力落实后再开启客户端原生购买。

## 需要老板和平台运营确认的产品决定

| 决定 | 建议 | 未确认时客户端行为 |
| --- | --- | --- |
| 对用户叫“余额”还是“积分” | 以平台 `quota_display_type` 与自定义符号为准 | 保持当前人民币展示，不写死积分 |
| 星途模型密钥是否必须属于当前登录账户 | 发行时优先要求同账户密钥，并提供可验证的绑定方式 | 显示账户级额度和归属提示，不承诺模型调用扣此余额 |
| 购买入口走平台网页还是原生支付 | 首版打开平台 `/wallet`，支付和条款留在平台 | 保持套餐只读和购买按钮禁用 |
| 多份订阅如何解释 | 逐份列示，扣费由服务端选择 | 不显示合计剩余额度 |
| 首批月包何时重置 | 每次购买一份额度，建议 `quota_reset_period=never`；自然月刷新型另行定价 | 不宣传“每月自动刷新”或固定 30 天 |
| 支付后的客服、退款和发票入口 | 指向平台正式页面或公司确认的服务渠道 | 不展示未经确认的按钮和承诺 |
