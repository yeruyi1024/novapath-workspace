# 星途官方升级同步与维护方案

日期：2026-10-15。状态：供评审的后续维护方案；仅编写流程，没有执行升级、修改运行时、创建定时检查或发布。文档后续随用户授权的工具恢复改动提交，提交评审不表示已实施本方案。

本文依据当前仓库源码、配置及已有验收记录整理，没有在线选择新的官方版本。文中的检查频率、自动化和分发能力均为建议；只有明确标为“已有”的能力才代表当前实现。下一次执行时先复核版本、配置和本仓库规范。

## 1. 目标与范围

以后采用“检查官方变化 → 选择固定版本 → 评估影响 → 隔离适配 → 验证 → 评审发布 → 观察与回退”的流程。我们负责选择适合星途的升级组合，并保留可追溯的来源和恢复路径。

同步范围包括官方 LobsterAI 桌面代码、OpenClaw 运行时及版本化补丁、随包和用户安装的插件与技能、本地及远程 MCP、依赖和发行资源。公司平台接口的变化只在星途客户端适配。

本方案的完成标准是：团队能明确每类升级的来源、操作边界、验证要求、发布条件和回退方式。具体升级仍须另建专项记录，填写实际目标版本与执行结果；本方案不替代升级验收，也不改变现有产品决定。

## 2. 当前基线与已有能力

| 项目 | 2026-10-15 核对结果 | 升级时的处理 |

| 随包插件 | `package.json.openclaw.plugins` 中逐项声明来源和版本 | 与运行时组成兼容组合，用户插件单独处理 |

| MCP 市场 | 管理页加载时获取远程列表并缓存；默认仍使用原有有道接口 | 市场目录刷新与已安装程序升级分别管理 |
| 用户插件更新 | 已有 npm、ClawHub 来源的检查和更新入口 | 不等于后台自动升级全部插件；Git、本地来源另记更新方式 |
| 技能同步 | 已有随包技能同步、用户技能升级、备份恢复和目录观察 | 本地目录观察不等于持续下载互联网最新版 |

| CI | 已有编译、测试、输出检查及平台打包工作流 | 没有自动合并上游代码的工作流；纯 Markdown 改动通常不会触发当前 CI |

## 3. 官方来源、职责与检查节奏

| 对象 | 来源登记 | 主要责任 |
| --- | --- | --- |
| LobsterAI 桌面代码 | 公司 README 登记的 `netease-youdao/LobsterAI` 官方仓库、release、tag 和提交 | 维护负责人比较变化，保留星途产品适配 |
| OpenClaw | `package.json.openclaw.repo`，当前为 `openclaw/openclaw` | 运行时负责人评估协议、迁移、补丁和 SDK |
| 插件、技能、本地 MCP | 各自 manifest、npm/Git/ClawHub 来源、固定版本或 commit、许可证 | 对应能力负责人维护版本、依赖和兼容性 |
| 远程 MCP / 公司 API | 服务提供方文档、变更通知、测试环境及接口契约 | 接入负责人核实认证、参数、返回和服务状态 |
| 星途应用分发 | 公司确认的星途发布源与更新服务 | 发行负责人发布星途构建，不向用户分发其他品牌的官方安装包来代替星途升级 |

建议每周检查一次发布说明和接口变更；每月集中安排一次兼容升级评估。安全修复、停用通知或真实故障发生时及时专项评估，不等待月度窗口。实际频率由维护负责人确认，本次不创建自动任务。

每条更新登记为“待评估、采用、延期、拒绝、已发布或已回退”，写明原因、负责人和下次检查条件。没有适合的新版本时保留当前组合，不为追版本修改稳定链路。

职责可以由同一个人兼任，但每次升级须明确谁做技术适配、谁记录验收、谁确认产品影响、谁批准发布。涉及文档能力替换或减少时，沿用当前老板评审要求。

## 4. 执行前的边界

- 另一个 new-api / gateway 平台及其 `maas-token` 克隆、分支、worktree 均只读。不得改文件、运行会写数据的命令或改变部署；接口缺口只记录，客户端能力范围另行说明。
- 当前回答、历史、流式、输入输出和插件/技能/MCP 执行遵循已确认的官方基线。只在单独立项并验证的升级中改变这些行为，不随品牌、布局或例行整理改造。
- 保留星途品牌、项目和对话组织、公司账户/模型适配及已确认的功能开关；同步官方代码不能顺带恢复已退役入口、外部账户、遥测或营销服务。
- 保留用户历史、凭据、文件和扩展启用状态。原始工作区已有未提交改动时，先登记归属，升级在独立目录准备；不得用清理命令覆盖它们。
- 不重建、替换或裁剪活动客户端使用的运行时，不反复重启用户客户端。测试资料和运行时独立，真实资料只在明确的升级操作中使用。
- 保留许可证和来源。当前办公技能的本地恢复不等于可发行；既有发行检查保持有效，未解决前不能发布包含相关材料的安装包。
- 遵守当前提交规则：授权后才提交、推送；代码推送个人 `origin`，向公司仓库提 PR，不向公司远程直接推送。

上述约束来自 [AGENTS.md](../../AGENTS.md)、[CONTRIBUTING.md](../../CONTRIBUTING.md)及[办公技能恢复记录](../../specs/bugfixes/2026-10-15-document-capability-restore.md)。本文不新增本次工作的批准步骤；未来升级按届时已获得的授权完成可审查结果，再处理必要的发布审批。

## 5. 每次升级的七个步骤

### 第一步：登记目标，保留旧组合

在 `specs/features/`、`specs/bugfixes/` 或 `specs/refactors/` 按改动类型新建带日期的专项记录。写清当前版本、候选版本、固定 commit、采用原因、影响范围、验收和回退。

保留上次可用的安装包、源码提交、依赖锁、插件/技能版本、补丁清单和运行时构建信息。上游桌面代码、OpenClaw 和插件不必同一天发布，也不必版本号相同；选择经过验证的组合。

涉及上游桌面升级时，记录它对 OpenClaw、Electron、Node、插件及状态 schema 的要求。必要的配套变化在同一兼容组合中验证，避免只提取表面功能却漏掉依赖。

### 第二步：比较官方旧版、官方目标版和星途当前实现

先比较官方旧版到候选版的变化，再与星途当前差异比较。把改动逐项归类：

| 类型 | 同步方式 |
| --- | --- |
| 官方缺陷或安全修复 | 核实问题、相关依赖和回归，再采用最小完整修复 |
| 官方新增功能 | 判断星途是否需要，确认入口、后台行为、资源和依赖 |
| 消息、工具、存储或 IPC 协议变化 | 作为完整链路适配，不能只复制单个文件 |
| 品牌、云账户、遥测、营销或不采用的入口 | 按星途既有决定处理，记录不采用原因 |
| 我们已有修复，官方已提供等价实现 | 验证等价后撤销本地重复改动，保留历史依据 |

小范围修复可以选择提交及必要依赖；大范围升级应以明确目标版本为基础整合，并逐项重放星途差异。不能仅因 Git 无冲突就认定兼容，也不能默认保留全部本地实现而丢掉官方修复。

回答和工具关键链路优先核对消息结构、附件、发送/停止/重试、思考与正文、流式合并/收尾、历史、工具参数与返回、Markdown、代码、表格和文件链接。现有官方一致性记录是检查起点，新的差异需重新验证。

### 第三步：准备隔离源码、构建目录和测试资料

使用专用星途 clone 或 worktree，配套一个可重建的 OpenClaw clone。候选代码、依赖、运行时输出及测试用户目录均与活动客户端分开。

现有脚本有两个必须考虑的行为：

1. `openclaw:ensure` 默认使用 `../openclaw`，切换版本时可能丢弃该源码目录的修改和未跟踪文件。必须指向专用、可重建的源码 clone；不要指向开发中的共享目录或含未保存工作的 worktree。
2. 完整运行时流水线会写入当前星途 checkout 的 `vendor/openclaw-runtime/` 并切换其 `current`。只设置 `OPENCLAW_SRC` 不能隔离输出；底层构建支持 `OUT_DIR`，但后续步骤并不因此全部隔离，优先隔离整个星途 checkout。

实施前可执行以下只读检查：

```bash
git status --short
git remote -v
git rev-parse HEAD
node --version
npm --version
```

当前没有名为 `upstream` 的 remote；升级时核对来源后，可在专用 clone 中登记官方只读 remote。不能把个人 `origin` 或公司 remote 误当官方上游，也不需要为了评估去改原工作区的 remote。

### 第四步：完成适配并固定版本

修改源码和配置源，不手改 `vendor/`、`dist/`、`dist-electron/` 或用户生成配置作为最终交付。依赖变化同步锁文件；移植上游提交保留来源和版权。

OpenClaw 升级先检查星途适配入口，再处理必须位于上游内部的版本化补丁。为每个补丁记录以下结论之一：

| 结论 | 所需依据 |
| --- | --- |
| 保留并适配 | 问题仍存在，补丁适配目标版本且回归通过 |
| 官方已解决，移除 | 找到官方实现和回归证据，移除后验证原问题不再发生 |
| 由星途边界层替代 | 有清晰、稳定的适配入口及兼容验证 |
| 暂不升级 | 缺少可行替代或关键验证，保留旧版并记录阻塞 |

补丁放在 `scripts/patches/<目标版本>/`，验证干净源码应用及重复执行行为。旧版文档中的跨会话 MCP 共享方案不能直接恢复；当前按请求者隔离的行为和凭据边界须核对。

以下是未来适配后的构建示例，只能在隔离星途 checkout 中执行；路径需替换为实际专用源码目录，目标版本先写入该 checkout 的 `package.json`：

```bash
export OPENCLAW_SRC="/absolute/path/to/dedicated-openclaw-clone"
npm run openclaw:runtime:host
npm run openclaw:sdk-contract
```

`runtime:host` 包含版本准备、补丁、构建、当前目标链接、网关打包、插件、本地扩展、预编译、渠道依赖和裁剪。构建缓存命中时核对版本、补丁及脚本指纹；确需强制重建时只对隔离目录使用 `OPENCLAW_FORCE_BUILD=1`。主机目标构建通过不能代表其他系统可运行。

### 第五步：验证行为、迁移和失败恢复

按专项范围先做定向验证，代码集成交付前运行仓库要求的完整门槛。以下命令用于未来升级，不是本次文档已执行的结果：

```bash
npm run build
npm run compile:electron
npm test
node --test scripts/ci-tests/*.test.cjs
git diff --check
```

TS/TSX 使用当前 CI 相同规则检查改动文件；准备依赖时使用锁文件和当前 Node/npm 要求，技能依赖按现有 CI 准备流程处理。不要在用户资料或活动运行时里执行安装和构建。

| 验证层 | 至少覆盖 |
| --- | --- |
| 对话与回答 | 真实模型请求、附件、流式、思考/正文、停止、失败重试、历史、工具结果、文件链接与预览 |
| 插件与技能 | 发现、启停、安装/升级失败、凭据和启用状态保留、备份恢复；文档能力覆盖原有范围 |
| MCP | 本地 stdio 与所用远程类型、工具发现、真实调用、通知后刷新、断线、认证失败、取消及子进程退出 |
| 数据与迁移 | 旧资料副本升级、迁移失败、重启、幂等； schema 兼容与回退演练 |
| 运行时 | 启动、配置同步、SDK 握手、真实命令执行、退出和日志；不能只测健康端点 |
| 公司适配 | 当前登录和模型调用、额度/套餐读取及错误提示；公司平台保持只读 |
| 平台与发行 | 对声明支持的平台分别记录原生安装、启动、依赖、签名、升级和卸载证据 |

补充“旧版星途配置 + 新服务”“新版星途配置 + 旧服务”等兼容用例，模拟失效密钥、工具参数变化和服务超时。真实外部调用使用已获授权的测试账号和数据；有写入或通知效果的工具用可控测试环境验证。

保留失败与复跑结果。单项通过、模拟测试、本地全库通过、GitHub CI 通过和平台安装验收分别记录，未执行项保持待验收。完整要求见[开发与发行验收](acceptance.md)。

### 第六步：评审、发布并更新基线

准备具体可审查的差异、来源、功能影响、测试证据、迁移说明、剩余风险和回退步骤。获得相应授权后推送个人仓库、创建公司 PR，按公司模板说明；不直接向公司远程推送。

升级官方行为基线时，同一改动更新相关基线记录和仓库规范，写清采用了哪些提交、还有哪些星途差异。不要在验证前把候选版本记成已完成。

先内测，再按公司确认的范围灰度，验证稳定后正式发布。内测包也必须满足适用的发行许可要求；当前办公技能发行阻断未解决前，不能用内测名义绕过。

公司更新服务完善后，客户端只获取我们验证发布的星途构建，不直接下载 LobsterAI 官方安装包或在运行中自行替换 OpenClaw。现有自动检查入口需配置更新地址；接通地址不能代替发布者验证、平台包验证和更新验收。

### 第七步：观察结果与回退

每次升级约定观察范围和时长，例如先观察一个工作日的内测使用，再决定是否扩大。关注启动/迁移失败、模型请求、工具调用、扩展加载和资料恢复；利用授权的本地日志与测试反馈，不自动开启当前关闭的遥测。

严重启动异常、数据异常、关键工具不可用或凭据失效扩散时停止扩大分发，按该次预案回退并保留证据。

回退必须区分两种情况：

- **尚未迁移用户资料：** 使用保留的旧完整构建及对应运行时/扩展组合恢复，不在活动进程下替换文件。
- **已经发生不兼容迁移：** 不能只降级安装包或手动改 schema 版本。关闭相关进程，依据演练过的方案恢复升级前一致性备份，或采用修复向前迁移；先保留升级后的资料，说明可能涉及的新增数据处理。

SQLite 备份使用现有一致性备份机制，不复制正在写入的数据库主文件来冒充完整备份。备份覆盖所需数据库、配置、扩展版本、工作区记忆等，并保护凭据；用户项目文件单独管理，不能随应用回退被覆盖。

远程 MCP 服务端的发布不能由客户端回退。服务方无旧接口或版本路由时，记录限制，临时关闭受影响连接并提示，必要时发布星途适配修复。

## 6. 各类扩展的专项同步规则

| 对象 | 推荐做法 | 保留与回退 |
| --- | --- | --- |
| 随包技能 | 逐项比较官方 `SKILL.md`、脚本、资源、依赖和许可，保留必要星途路径适配；新版本只在完整验证后纳入客户端 | 沿用原子替换和 `skill-backups/`；凭据及用户启用状态不重置；缺依赖明确报告 |
| 用户技能 | 展示来源、版本、变更和更新入口；来源不支持版本比较时明确说明 | 不用随包同名技能强行覆盖；升级失败恢复旧目录 |
| 随包插件 | 固定来源/版本或 commit，核对目标 OpenClaw SDK 和依赖，更新锁及相关配置 | 保留上一组合、用户配置和必要的迁移记录 |
| 用户插件 | 沿用已有检查/更新流程；Git 和本地来源单独登记，不冒充统一支持 | 不在用户对话中静默升级可执行代码；失败可恢复原状态 |
| 托管安装的本地 MCP | 记录原始启动配置、实际解析版本、安装目录和来源；在独立目录准备新版本，调用验证后切换 | 当前没有完整自动升级/回退机制，后续专项实现；不要把现有“重试”按钮当作强制升级按钮 |
| 原始命令启动的 MCP | 记录所依赖的 Node/Python/uvx/CLI 和版本；若命令含浮动版本，注明启动时可能由外部工具解析变化 | 生产推荐选择可复现的版本；不能保证外部包缓存的长期可恢复性 |
| 远程 MCP | 跟踪 URL、传输、认证、工具 schema 和返回；工具发现只是兼容验证的一部分 | 优先利用服务方版本接口；静态 API Key 更新与 OAuth 刷新分别处理，企查查属于专用接入 |

当前 `McpLaunchResolverManager` 在同指纹且结果就绪时直接复用，即使原配置包含 `@latest` 也不等于定期升级。未来本地 MCP 升级应提供明确动作、固定版本、独立准备、验证后切换和失败恢复，不能通过删除用户配置或随意清库实现。

## 7. 自动化分阶段建设

以下均为建议待办，未随本文实现或开启：

| 阶段 | 建设内容 | 验收条件 |
| --- | --- | --- |
| A：先有台账 | 登记官方来源、版本、commit、兼容组合、采用/延期原因和验证证据 | 任一发行版能追溯到完整来源、补丁和锁文件 |
| B：自动检查与报告 | 定期只读检查 release、目标依赖、接口停用通知，输出候选清单；由负责人按范围安排评估 | 不改主分支、不安装到用户目录；来源失败不误报“已是最新”，避免重复通知 |
| C：候选升级自动验证 | 经授权创建升级分支/PR，在隔离 CI 准备依赖与运行时，运行兼容测试和差异报告 | 凭据隔离、版本固定、产物可追溯，失败不合并；原生验收仍明确记录 |
| D：星途受控分发 | 建设公司更新源、发布元数据及发布者验证、平台/架构检查、包完整性验证、灰度与撤回机制 | 旧版到新版和中断恢复实测通过；签名/校验失败停止更新，有明确恢复路径 |

自动检查可以减少遗漏；合并、功能取舍和升级后行为仍由维护与发行流程负责。大型运行时升级、存储迁移及有业务影响的扩展升级不默认无人值守发布。
